Blackbox · v0.21
Why

The interesting part happens before you notice

When a machine stalls, the question is: “which tasks were runnable and couldn’t get a CPU?”
  • By the time you attach perf, the window you needed has already slid past.
  • Who was holding the CPU? What was stuck on I/O? Unanswerable after the fact.
  • Servers go through seconds of complete unresponsiveness — and nobody kept the tape.
🎯 Blackbox is always running, so the history is already there when the stall happens.

Blackbox2
What it does

A tiny tape recorder strapped to the scheduler

Four moves, nothing more — and each one is deliberately small.

1Capture

Watches sched_switch through one tracepoint (no kprobes), plus fork / exec / exit lifecycle events on their own stream.

2Retain

Keeps a rolling last-N window in userspace — capped by both event count and seconds, so memory is predictable.

3Trigger

Writes a trace the moment PSI pressure (CPU / memory / I/O) or an OOM kill crosses a threshold — or when you ask.

4Export

One self-describing JSON dump → plain-text report or a Perfetto timeline you drag into ui.perfetto.dev.

🧠 All of the hard logic — intervals, ranking, hysteresis — is pure user-space Rust. The BPF side only stamps and copies 64-byte records.

Blackbox5
Design

Two decisions most of the architecture follows from

1The ring buffer is transport only — history lives in user space

A BPF ring buffer cannot retain history: it overwrites the oldest unread records. So the real “last N seconds” is a bounded VecDeque in blackbox-core, refilled continuously.

⚠Honest consequence: history exists only while blackboxd is running. A killed daemon leaves a short window.

2All the hard logic is pure, testable Rust

Interval reconstruction, ranking consumers, PSI hysteresis, report formatting — everything that costs verifier budget and runtime sits in blackbox-core, which runs with no privileges.

🧪That split is why the whole brain of the tool is covered by ordinary cargo test — 180 tests, zero root.
Blackbox6
Reconstruction

Switches in, answers out

  • Consecutive switches on a CPU are rebuilt into on-CPU intervals — who actually held each core, for how long.
  • prev_state separates the two failure modes:
    ⚡prev_state = 0 → task was runnable and lost the CPU → scheduler latency (→ longest-delay ranking)
    💤prev_state ≠ 0 → task slept / waited on I/O → blocked time
  • Lifecycle events ride their own stream and render as instant markers — a fork storm or a respawning daemon shows up next to the CPU picture.
# longest scheduler delays 2.0 ms pid 0 swapper/3 1.8 ms pid 69434 dav1d-worker 1.4 ms pid 72208 trigger-poller
# top cpu consumers (from the same trace) 63.72% swapper/3 2.56 s 10.91% trigger-poller 438.9 ms 6.38% bpf-collector 256.5 ms 3.88% gnome-terminal- 155.9 ms

Note the daemon measuring itself — trigger-poller and bpf-collector appear in the ranking. That’s honesty by construction.

Blackbox7
Triggers

The dump fires itself — with hysteresis

🧠
CPU pressure PSI /proc/pressure/cpu

avg10 over threshold  ·  default 80%

🧮
Memory pressure PSI

runnable-or-blocked-on-memory skew · default 20%

💾
I/O pressure PSI

tasks stalled on I/O · default 20%

☠️
OOM kill /proc/vmstat

any advance of the oom_kill counter fires — needs no BPF, reports the kill count

✋
Manual blackbox dump

take the trace now, whenever you want

Hysteresis — no dump storms

A trigger must stay over threshold for consecutive samples (default 4 × 250 ms) before firing, and it re-arms only once pressure recedes below the threshold. A sustained stall dumps once, not forty times.

over×4→fire ✓· recedes →re-arm

Every dump is self-describing

Schema version, trigger reason + time, host identity, window bounds (monotonic and wall-clock), and the daemon’s own overhead counters ride along with the events.

After it fires

One trace, two ways to read it

The dump · JSON schema v2
{ "schema": 2, // v1 traces still load "trigger": { "reason": "psi_cpu", … }, "host": { "hostname": …, "os": …, "kernel": … }, "window": { "start_mono_ns": …, "start_wall_utc": …, "end": …, "truncated": false }, "events": [ 64-byte sched_switch … ], "lifecycle": [ fork / exec / exit … ] }

📄 Text report · blackbox report f.json

  • Top CPU consumers, per CPU or whole-host
  • Longest scheduler delays — runnable tasks waiting on a CPU
  • Most blocked time; lifecycle section; --top N

📈 Perfetto · blackbox report --perfetto

Chrome-format JSON you drag straight onto ui.perfetto.dev: per-CPU scheduling lanes, blocked/sleep states, and lifecycle instant markers.

$ blackbox report incident.json --perfetto > t.json # → drag t.json onto ui.perfetto.dev
🔒Runs offline and unprivileged — the exporter is pure Rust, no daemon needed to re-read a dump.
Blackbox9
Operations

Four commands in, clean lifecycle out

$ sudo blackbox start # detached daemon · --foreground for services $ blackbox status # health · collection · last trigger $ blackbox dump -o inc.json # manual trace NOW $ blackbox report inc.json # text … $ blackbox report inc.json --perfetto > t.json # …or Perfetto

🛰 Daemon + CLI

Line-delimited JSON over a Unix socket; three threads (collect · trigger-poll · IPC) share one locked Runtime.

🪂 Graceful degradation

No object / no privileges / no BTF? BPF stays off, PSI + OOM dumps and status keep working — and status says exactly why.

🧹 Clean shutdown

SIGINT/SIGTERM stop both workers in a few hundred ms, remove socket + pidfile; dump retention keeps the newest K; systemd unit included.

🎚Config — history, pressure, dump, bpf sections. Missing file = defaults; unknown key = hard startup error.
🎯PID filter — [bpf] filter_pids narrows machine-wide tracing to a few processes (more on the next slide).

Cost

It reads every switch — so it is not free

Cost scales with the machine-wide context-switch rate, not CPU load. Measured on an 8-core host running a switch-only workload (400k switches / run):

+26–63%
switch-heavy workload
noisy shared host — treat as indicative · ~0.6–1.7 µs per switch caused
~0.6
core, daemon CPU
the stable figure across runs · lifecycle tracepoints add nothing measurable
≈ 0
compute-bound workload
blackbox runs no code on compute — the control is untouched

🎯 The mitigation: PID filter

Set [bpf] filter_pids and only those pids’ events reach the ring, the decode and the history.

66% → 0.15%
daemon CPU (one core)
+26–41% → +1.5–4.7%
workload cost

The tracepoint still fires either way — the filter removes the ingest, not the hook.

🧪 And the tool tests itself

Writing the benchmark found a real bug — a PSI poller that spun because a continue skipped its sleep — and fixing it cut daemon CPU from 1.6 → 0.6 cores. The daemon’s own threads show up in its reports, measured with the same yardstick.

$ sudo scripts/bench.sh $ sudo FILTER_PIDS=999999 scripts/bench.sh

Get started

Try it in five commands

Quick start
$ sudo blackbox start # daemon up, BPF attached $ blackbox status bpf collection attached events retained 12 431 $ blackbox dump -o /tmp/inc.json $ blackbox report /tmp/inc.json top cpu consumers: swapper/3 63.7% …
You need
  • Linux ≥ 5.15 (BPF ring buffers + BTF + PSI); CO-RE needs /sys/kernel/btf/vmlinux
  • CAP_BPF + CAP_PERFMON (or just root) to load BPF — reading PSI and reports need nothing special
  • Prebuilt release tarball, or build: stable Rust + nightly/rust-src + bpf-linker for the object
  • A couple of seconds: sudo blackbox start then blackbox status ← if it says “attached”, you’re recording
🧭No root on the demo box? BPF load is blocked (common on shared kernels) — validated in a privileged container instead; --no-bpf still demos PSI + dumps.
Blackbox12
Where it stands · v0.2

Small, honest, and shaped for what’s next

🔭 In v0.2

  • sched_switch + lifecycle capture
  • PSI (CPU / mem / IO) + OOM + manual
  • bounded history, schema-v2 dump
  • text + Perfetto reports
  • PID filter · dump retention

🕶 Privacy posture

Records pids, comms, CPU ids, timestamps — and an exec path truncated to 15 chars. No arguments, no stdin/stdout, no file contents, no container names. A post-mortem of scheduling, nothing more.

🧭 Honest edges → roadmap

Window lives only while the daemon runs · kernel ring drops aren’t observable via aya (reported 0) · PID filter is coarse (pids aren’t stable) · next: block I/O event sources, cgroup scoping, sampling, persistent history, remote shipping.

The recorder is always on — so the moment you need is never lost.
